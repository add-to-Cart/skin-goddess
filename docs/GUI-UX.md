## Registration safeguards and quieter interface — 2 November 2026

Owner requested duplicate prevention, authorized client removal, no input placeholders, a flat login and clearer visual controls. The owner then explicitly selected **block matching full name plus matching phone/email; warn on name alone**, and **administrator-only archiving with confirmation**. These decisions supersede any earlier proposal to block an exact name-only repeated record.

### Implemented behavior

- ClientController checks new registrations against active and archived clients. Name comparison ignores case/repeated whitespace; phones compare digits without punctuation; email comparison ignores case. A matching full name plus either matching nonempty contact returns 409 and the existing ID/active state, without updating/merging the original person. Shared names with different contacts and different names sharing a phone remain possible. Country-code conversion, fuzzy identity inference and cleanup of old duplicates are not included.
- ClientForm checks for same-name active clients before creating, offers their existing profiles and requires “This is a different person” confirmation to continue a separate registration. A server duplicate response offers the existing active profile, or administrator review for an archived record. No contact is required by a newly invented identity policy.
- The form stores the original registration payload and random key in per-user session storage before submitting. An uncertain result locks those original fields across close/reopen, with Retry and a history-review acknowledgement before discarding. Server request-key replay returns the original client, and altered payload/key reuse is rejected. Registration attempts are serialized using the existing shared cache lock. Cache keys store only a fingerprint and client ID, not the client payload. Default database-cache writes and client creation share a database transaction. No schema or dependency change was introduced.
- DELETE clients is now in the existing administrator-only middleware group. The profile shows an archive icon only to administrators and confirms the exact client plus preserved history before sending. Archiving retains the client row, sale/debt, payment and treatment records and removes the client from active lists. This is not permanent deletion and adds no restoration workflow.
- All JSX input/textarea/select placeholder props have been removed. Required labels remain; existing notes guidance remains below its field, payment-reference and correction-reason guidance is outside controls. Duplicate/recovery feedback appears only when needed. Login is flat, with no panel border, shadow or separate card background; repeated introduction/footer copy was removed. Person symbols identify client records, and pencil icons replace routine Edit labels across client, reminder, expense, treatment, service and account controls. Icon controls retain accessible names, tooltips and touch sizing. Financial/status text and consequential actions remain explicit.

### Proposed consistent interaction

| | Always visible | Show details / Hide details | Contextual navigation |

Use the same chevron-plus-**Show details** control on both lists; change to **Hide details** when open. Names/sale identifiers and “Open…” links use navigation styling, with an external-direction chevron where helpful. Do not make the entire row/card clickable. Keep existing rose branding and semantic status colors. ### Desktop, mobile and keyboard behavior

- Desktop: retain compact comparison tables. Client columns: Client identity, Phone, Status, Actions; existing notes stay visible beneath identity when present. Sales columns: Sale/date, Client, Billed, Recorded payments, Outstanding, Status, Actions. Secondary details occupy a separate row directly beneath their owning record, with a correctly spanned table cell. Numeric columns align consistently; headings explain every peso figure.

Identity/date/status lead, followed by labeled financial rows and visible warnings, then separate Show details and Open actions. Stack actions where needed, use at least 44 px touch targets and wrap long names/amounts. Expanded content stays inside the card, without horizontal page overflow. Test tablet widths explicitly; other screens retain their existing breakpoint behavior.

Enter/Space toggles, Tab reaches links and controls, and focus stays on the toggle after expansion/collapse. Collapsed content must be hidden from both focus and the accessibility tree. The chevron is not a separate focus target. Use semantic table headers; never nest buttons inside navigation links or require hover to read details. Keep visible focus styles and a contextual accessible name such as “Show details for Sale #42.”

A failed summary shows **Balance unavailable — Retry** on that sale; its authoritative paid/outstanding values remain unavailable until recovery. Do not display a current-looking payment status if its summary failed. Do not hide that sale, its known billed amount or navigation. Per-sale summary requests add latency and do not create an atomic list-wide snapshot; existing backend save validation remains authoritative.

### Why this reduces effort and prevents mistakes

Staff recognize a person or sale before reading every field. IDs and phone numbers distinguish duplicate names and repeated purchases. Email/address or sale contents can be checked without navigating away and losing list context. Billed, received and owed figures remain visible together; canceled debt cannot be mistaken for a settled account. Explicit expansion/navigation controls prevent accidental navigation and support keyboard users. Save/refresh feedback reduces duplicate entries after uncertainty. ## Proposed information hierarchy — recommendations

**Improve the client profile first**, with small shared-form accessibility work alongside it. This is where staff can verify the person, select the right allowance and collect a payment without confusing three different things.

1. Compact identity header: name, client ID, phone, status; visible clinic notes when present. Keep Edit secondary. Offer Record Treatment, Record Payment and New Sale / Purchase Package without duplicating the same ambiguous action. Payment selection must identify one sale; never allocate it across packages automatically.
2. Clearly labeled financial summary: **Total billed / Recorded payments / Outstanding payment** across all the client's sales, excluding voided payments from received money. Use existing authoritative per-sale summaries; do not infer debt from status badges or package prices alone. Profile currently fetches financial summaries only for packages; obtaining the ordinary-sale summaries is needed for an honest all-client total. Show unavailable figures as unavailable, never zero. More per-sale requests are a known cost; propose any later API aggregation separately.
3. Usable packages near the top: treatment, purchase ID/date, valid completed/included/remaining, price/paid/owed and a labeled action for that purchase. Keep payment status separate. Completed/canceled purchases remain easily accessible as history, with counts and unused-not-redeemable text; no default disappearance of outstanding canceled debt. On canceled/exhausted packages, payment/history remains accessible while new completion stays blocked.
4. Treatment Records, Sales & Payments and Follow-ups sections with readable mobile alternatives. Show recent records initially if necessary, with explicit Show all access; never remove audits or calculate progress from the visible subset.

Example to display: **Package ₱12,000 · Recorded payments ₱4,000 · Outstanding ₱8,000** and, separately, **2 of 6 valid sessions completed · 4 remaining**. A reversal stays in history without counting as completed. A canceled package says “Unused sessions: 4 — cannot be used”; its ₱8,000 debt remains visible.
