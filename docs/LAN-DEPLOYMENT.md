# Skin Goddess: private LAN deployment plan

Audit: 20 October 2026. **Approval required before implementation.** Only this document was created. No application, Apache, MySQL, firewall, router, dependency, or PWA changes were made. Existing unrelated workspace changes were preserved.

## How the system will operate

The clinic server is Windows computer `LAPTOP-N7DNI4DC`. Laragon runs Apache/PHP and MySQL on that computer. Authorized browsers connect to Apache; Laravel alone connects to MySQL over loopback. Client devices need neither MySQL nor an application installation. The server must stay powered on and awake during clinic hours.

Proposed path: clinic device → private clinic Wi-Fi/router → Apache → Laravel → local MySQL. React assets and `/api` requests use the same browser origin. Internet access is not required for local application traffic; external services such as email can still require it.

## Network decisions before implementation

1. Confirm this is the clinic router/subnet. Prefer reserving the server's **current `192.168.1.96`** in router DHCP rather than assigning an arbitrary static address. Verify availability/reservation rules in the router. Reserve the adapter actually used; Wi-Fi random hardware addresses must remain stable for this SSID. Prefer wired Ethernet if practical, with a separate reservation for its adapter.
2. Identify the trusted staff SSID/VLAN and approved device addresses. Do not authorize the whole `192.168.1.0/24` unless it contains only trusted clinic devices. A guest/shared SSID is unsuitable. Prefer a dedicated staff segment; otherwise reserve approved client IPs and use a matching allowlist in Apache and Windows Firewall. IP allowlists supplement Wi-Fi access controls and application login; they do not establish device identity.
3. On the router/AP, confirm staff devices can communicate with the server. Check AP/client isolation, VLAN routing and ACLs. Keep guest isolation enabled and guest-to-server traffic denied. Do not globally disable isolation just to make the app work. Test a real staff laptop and phone; server-side requests cannot prove Wi-Fi reachability.
4. Prefer router-local DNS record `skin-goddess.home.arpa` → reserved server IP, delivered through DHCP DNS. This needs no public DNS. Router capability is unverified. If unsupported, use the reserved IP as the initial address and include that IP in the HTTPS certificate. Windows hosts entries are an optional per-computer workaround, not a practical phone strategy. Do not assume single-label `skin-goddess`, the Windows hostname, or `.local` resolves across Android/iOS/Windows. Private DNS, VPNs or encrypted DNS can bypass router DNS and must be checked on clients.
5. Use trusted internal HTTPS for actual credentials and patient data. Keep the existing Apache stack; plan a private CA/server certificate with SANs for the chosen name and reserved IP, installed through Laragon's certificate facilities or existing Windows tooling. Trust the CA on each authorized Windows/Android/iOS device and verify browser trust; iOS may require explicit full trust. Protect the CA key. Do not bypass certificate warnings. Laragon's existing port 443 listener does not establish a trusted clinic HTTPS vhost. HTTP may be used for non-sensitive connectivity diagnostics only. HTTPS also prepares for future service workers; private-IP HTTP is not the localhost secure-context exception.

## Verification procedure after approval and implementation

Use test accounts and non-sensitive test data. Record device, network, address, time and result; do not capture passwords, tokens or patient records. Proposed addresses below become valid only after the router/vhost/TLS work; they are not working deployment links today.

1. **Start:** on the server open Laragon and Start All (Apache and MySQL). Before the first implementation restart, run the actual Apache binary with `-t` and `-S` in the normal administrator/Laragon environment. Both must succeed and show the intended clinic/default hosts. Do not reinstall anything or run migrations.
2. **Server check:** open the existing local clinic address and then the canonical HTTPS address, preferably `https://skin-goddess.home.arpa/`. Confirm correct branding, no certificate warning, assets loaded, login succeeds and a read-only page loads. Keep `APP_ENV=production` and `APP_DEBUG=false`; a controlled nonexistent API path must not reveal stack traces/configuration.
3. **Find IP:** run `ipconfig` on the server. Confirm Wi-Fi/Ethernet IPv4 matches the reservation. Run `netstat -ano -p tcp`: SQL ports 3306/33060 must listen only on `127.0.0.1`; identify unexpected IPv6 listeners too. Confirm firewall state/profile/scopes in Windows Defender Firewall with Advanced Security.
4. **Other Windows computer:** connect to the approved staff Wi-Fi. Run `Test-NetConnection 192.168.1.96 -Port 443` (expect `TcpTestSucceeded: True`). Run `Resolve-DnsName skin-goddess.home.arpa` if local DNS is configured (expect reserved IP). Open the canonical HTTPS address. Optional ping failure is inconclusive because ICMP may be blocked. TCP 80 should fail unless the approved redirect exists; if retained, verify it redirects to the canonical HTTPS origin.
5. **Android/iPhone:** connect to the same approved staff network, temporarily turn off mobile data to prove the path, and open the same HTTPS address. Confirm trusted certificate, responsive login, assets, read-only navigation and refresh of a nested SPA route. Verify router DNS use if name resolution fails. Restore normal phone connectivity after testing.
6. **Authentication/API:** in a fresh private browser session, request `/api/auth/me` and `/api/clients` with `Accept: application/json` and no token: expect 401 and no clinic records. Sign in normally; browser Network tools should show successful protected requests with Authorization preserved. Staff requests to admin-only `/api/auth/users` must return 403; an authorized admin should succeed. Log out and verify ordinary navigation returns to login. Existing logout clears browser credentials but does not revoke an already copied token; do not treat logout as a revocation guarantee or change that behavior in this phase.
7. **Private paths/tools:** remotely request `/.env`, `/.git/config`, `/storage/logs/laravel.log`, `/composer.json`, `/adminer` and `/phpmyadmin`. Expect 403/404 after explicit denials; no secrets, logs, source, SQL dumps, admin UI or directory listing. Check response content as well as status because the current SPA fallback can return HTML with 200. Confirm unknown Host headers/default site cannot expose Laragon or other projects.
8. **Database isolation:** from the second computer run `Test-NetConnection 192.168.1.96 -Port 3306` and again for `33060` and `8025`: expect False. Confirm Laravel still reads data locally. Do not attempt remote database login or open SQL ports for troubleshooting.
9. **Denied networks/internet:** repeat web-port tests from guest Wi-Fi and an unapproved device/segment: expect failure or explicit denial and no clinic content. Disconnect the phone from Wi-Fi and use mobile data: private clinic address must be unreachable. Also inspect router WAN forwarding/DMZ/UPnP rules and IPv6 firewall; a mobile-data failure to an RFC1918 address alone does not prove no public exposure. If a public WAN address exists, an authorized external test of that address's web/SQL ports should fail, including IPv6 where assigned. Do not create forwarding to perform the test.
10. **Recovery:** confirm the daily backup completes, copy it to protected off-computer storage, and restore into a separate empty database following README. Validate records and totals without replacing the live database. Hardware tests, successful authenticated flows, certificate trust, router restrictions and restore recovery remain **pending** until recorded.

## Daily operation and troubleshooting

- Start the host, connect it to the reserved clinic network, start Laragon's Apache/MySQL, and check the canonical address. Clients use browser bookmarks. Do not use `php artisan serve`, `npm run dev` or Vite preview for clinic service.
- Stop only after staff finish saving and the backup completes. Use Laragon Stop All before shutting Windows down. Agree on operating hours and prevent server sleep during them; never abruptly power off while saving. A UPS is useful if power is unreliable.
- **Timeout:** check server power/sleep, Laragon, correct reserved IP, staff SSID, firewall profile/scopes, AP isolation/VLAN ACLs and port 443. Do not disable the firewall.
- **IP works, name fails:** check router DNS record/DHCP DNS and phone private DNS/VPN settings. Do not change public DNS records.
- **Laragon welcome page/wrong app:** check vhost address matching, ServerName/alias and default vhost order. Validate config before restart.
- **403:** compare the client's actual source IP with Apache/firewall allowlists; do not replace restrictions with unrestricted access.
- **Blank page/asset 404 or 503:** check `public/clinic/index.html` and referenced `public/assets` files. Review the existing build procedure before an approved rebuild.
- **401/403 after page loads:** log in at the canonical origin and check account active state, role, expiry and Authorization forwarding. Do not remove middleware or broaden CORS.
- **Certificate warning:** verify DNS/IP SAN, device time and CA trust. Do not continue with clinic credentials until fixed.
- **Database error:** check local MySQL is running, its loopback binding and unchanged Laravel DB settings. Never publish 3306/33060 as a remedy.
- Review recent Apache error logs and `storage/logs/laravel.log` locally; do not share patient data or environment secrets. Back up files before later approved changes. On failure, remove new LAN access and restore saved configs; validate Apache before restart. Do not restore broad database exposure as a rollback shortcut.
